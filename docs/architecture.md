# Устройство панели

Документ описывает, что есть в коде сейчас и что запланировано. Запланированное помечено словом «план».

## Роли серверов

При установке выбирается роль:

- **Основной сервер** (за границей). Выпускает трафик в интернет, держит панель и базу, служит источником для CDN.
- **Точка маршрутизации** (в РФ). Принимает подключения пользователей и пересылает их на основной сервер по каскаду.

Каскад между ролями настраивается автоматически (план).

## Что работает сейчас

- Go-бинарник `tigersb`: `init`, `serve`, `info`, `open`, `close`, `site`, `passwd`, `sleep`, `wake`, `status`, `xray`, `singbox`, `mieru`, `edge`, `sub`.
- Веб-панель на `127.0.0.1` со случайным портом и секретным путём. Снаружи открывается через Caddy по `https://<домен>/<секретный путь>/`, пока админ не закроет её (`tigersb close`, настройка `panel.open` в базе). Пока панель закрыта или спит, Caddy отдаёт по секретному пути заглушку. Открыть снова можно только по SSH (`tigersb open`). Запасной вход через SSH-туннель работает всегда. Вход по логину и паролю (Argon2id, лимиты попыток).

  Когда запрос пришёл через Caddy, панель не может перезагрузить Caddy синхронно: Caddy ждёт завершения этого же запроса. Поэтому она проверяет новый Caddyfile через `/adapt`, записывает файлы, отвечает и только потом вызывает `/load`.
- SQLite: администраторы, сессии, пользователи VPN с токенами подписок и устройства (`internal/store`).
- Режим сна: `tigersb sleep` останавливает процесс панели, VPN и подписки продолжают работать.
- Установщик `scripts/install.sh` (установка, `--update`) и `scripts/uninstall.sh`.
- Контроль (`internal/metrics`, `internal/health`, `internal/update`):
  - `tigersb-monitor.timer` раз в 5 минут запускает `tigersb monitor`. Он записывает замер из `/proc` в таблицу `metrics` (7 дней), проверяет сервер и кладёт отчёт в `settings` (`health.last`), а раз в 6 часов спрашивает GitHub о новой версии (`update.check`).
  - Обновление и откат панель не делает сама. Она записывает задачу в `/var/lib/tigersb/update/status.json` и запускает `tigersb-update.service` (`tigersb job`), который работает в своём cgroup и переживает перезапуск панели. Установщик собирает новую версию из исходников коммита; модули и кэш Go на время сборки лежат в `/var/cache/tigersb` и удаляются после неё (у службы нет `HOME`, поэтому пути заданы явно).
  - Статус и журнал лежат в файлах, а не в базе, потому что откат заменяет базу.
  - Точки восстановления: `tar.gz` в `/var/lib/tigersb/restore` с манифестом. База копируется через `VACUUM INTO`, поэтому панель не останавливается. При возврате распаковываются только известные пути, а набор служб `tigersb*` становится ровно таким, как в точке.
  - Сборки из `main` называются `main-<короткий хеш>`. По хешу панель понимает, есть ли обновление, а установщик с `--ref` собирает ровно проверенный коммит.
- Caddy 2.11.4 (служба `tigersb-caddy`, бинарник в `/usr/local/lib/tigersb`): с доменом на `127.0.0.1:8444` за `tigersb-edge`, без домена на порту 80. Панель пишет `/var/lib/tigersb/caddy/Caddyfile` и `/var/lib/tigersb/www/index.html` и применяет их через admin-сокет `/run/tigersb-caddy/admin.sock` (`internal/site`). Сертификат Let's Encrypt через TLS-ALPN (`alt_tlsalpn_port 8444`: проверка приходит на 443 и через edge попадает в Caddy), порт 80 закрыт. Настройки сайта хранятся в таблице `settings`.
- Порт 443 (`internal/edge`, служба `tigersb-edge`, только `CAP_NET_BIND_SERVICE`). Читает SNI из ClientHello и пересылает подключение, не расшифровывая его:
  - домен панели → Caddy `127.0.0.1:8444` с заголовком PROXY v1 (Caddy принимает его только с `127.0.0.1` через `listener_wrappers proxy_protocol`, подключение без заголовка тоже обслуживает);
  - SNI протокола на 443 → внутренний порт Xray (gRPC `10441`, XHTTP `10442`) с заголовком PROXY v1, чтобы Xray видел настоящий IP клиента;
  - остальное → протокол на 443 (XHTTP, иначе gRPC, иначе Caddy).

  Маршруты лежат в `/var/lib/tigersb/edge/routes.json`, edge перечитывает их раз в 2 секунды.
  Кроме 443 edge держит порты из `/var/lib/tigersb/edge/ports.json` (`edge.Forward`): сейчас это TCP-порт NaïveProxy, который пишет `Sync` sing-box. Подключение уходит на внутренний порт целиком, без чтения ClientHello и без заголовка PROXY, с `TCP_CONGESTION` из маршрута. Порты открываются и закрываются при каждом перечитывании; занятый порт (например, пока sing-box после обновления его не отпустил) пробуется снова. `Forward.Gen` — хеш конфига и сертификата sing-box: sing-box после SIGHUP оставляет открытыми HTTP/2-соединения NaïveProxy, но новых потоков на них не открывает, а клиент продолжает ими пользоваться. Когда `Gen` меняется, edge закрывает открытые соединения порта, и клиенты подключаются заново. `Sync` пишет файл после перечитывания sing-box.
  У маршрута может быть `congestion` (`bbr`): edge ставит этот алгоритм (`TCP_CONGESTION`) на подключение клиента, если в протоколе включён BBR. Протокол не на 443 получает BBR через `sockopt.tcpCongestion` в inbound Xray. Ядро должно разрешать `bbr` в `net.ipv4.tcp_allowed_congestion_control`: это делает установщик, панель показывает состояние (`bbr_ready`).
- Xray-core (`internal/xray`, служба `tigersb-xray`). Официальный образ `ghcr.io/xtls/xray-core` закреплён по хешу; `docker run --network host --read-only --cap-drop ALL --log-driver none`, конфиг `/var/lib/tigersb/xray/config.json` смонтирован только для чтения. Docker ставится из пакетов дистрибутива, `DOCKER_CONFIG` у служб панели указывает в `/var/lib/tigersb/docker`.
  - Настройки протоколов — JSON в `settings` (`xray.protocols`), пользователи — таблица `users`. Конфиг собирается из них целиком (`xray.Render`).
  - Протокол не на 443 слушает свой порт сам, протокол на 443 слушает `127.0.0.1` и внутренний порт.
  - Сохранение протоколов: `xray run -test` в одноразовом контейнере без сети, запись файлов, перезапуск службы.
  - Пользователи добавляются и удаляются без перезапуска через API Xray на `127.0.0.1:10085` (`xray api adu`/`rmu` внутри контейнера). Конфиг на диске всё равно переписывается, чтобы перезапуск ничего не потерял.
  - `rmu` закрывает только новые подключения: открытые соединения пользователя (долгая загрузка по XHTTP, поток gRPC) продолжают работать со старым ключом. Закрыть соединения одного пользователя Xray не умеет, поэтому после `rmu` панель спрашивает `xray api statsonline -email u<id>` и, если соединения есть, перезапускает Xray с конфигом на диске, где пользователя уже нет (`Runtime.remove`). При перевыпуске ключа после такого перезапуска `adu` не нужен.
  - ID пользователей не повторяются (таблица `user_ids`): SQLite отдал бы ID удалённого последнего пользователя новому, а ядра знают пользователя по `u<id>`, и счётчики Xray удалённого достались бы новому.
  - Тестовые ссылки вкладки «Протоколы»: настройка `test:<протокол>` хранит UUID. В конфиги ядер они попадают как пользователи с полем `Only` (`store.CoreUsers`), только в inbound своего протокола и с именем `test-<протокол>`, поэтому статистика их не видит. Новая ссылка меняется на лету через `rmu`/`adu` (Xray) или перечитыванием конфига (sing-box).
  - Статистика: `statsonlineiplist` (IP в сети) и `statsquery -reset` (трафик), email пользователя в Xray — `u<id>`. Собирает панель при открытии вкладки и `tigersb monitor` раз в 5 минут.
  - Сканер SNI: рукопожатие TLS без SNI с адресами подсети /24, проверка TLS 1.3, HTTP/2, X25519 и сертификата (идея RealiTLScanner).
- sing-box (`internal/singbox`, служба `tigersb-singbox`): TUIC v5 на UDP 8443, Hysteria 2 на UDP 443 и NaïveProxy на TCP 2443. Официальный образ `ghcr.io/sagernet/sing-box` закреплён по хешу; тот же `docker run --network host --read-only --cap-drop ALL --log-driver none` плюс `NET_BIND_SERVICE`, каталог `/var/lib/tigersb/singbox` смонтирован только для чтения.
  - Общее у ядер (`internal/core`): запуск docker, `Link`. Каждое ядро — свой пакет того же вида: настройки, `Render`, `Runtime` (`Test`, `Sync`, аргументы `docker run`) и ссылки. Новый протокол добавляется в ядро, которое его поддерживает.
  - Настройки — JSON в `settings` (`singbox.protocols`) с секретом; пароль TUIC пользователя — `HMAC-SHA256(секрет, "tuic:"+uuid)`, Hysteria 2 — `HMAC-SHA256(секрет, "hysteria2:"+uuid)`, NaïveProxy — `"naive:"+uuid`, Mieru — `"mieru:"+uuid`, имя — `u<id>`, как в Xray. Пароль Salamander по умолчанию — `HMAC-SHA256(секрет, "salamander")`: так его одинаково получают панель, подписки и контейнер, даже если настройки сохранены до появления Hysteria 2; кнопка «Новый пароль» записывает случайный.
  - Сертификат: самый свежий действующий сертификат домена из хранилища Caddy (`caddy/certificates/<issuer>/<домен>/`) копируется в `singbox/tls.crt` и `tls.key`. Без домена или сертификата inbound TUIC, Hysteria 2 и NaïveProxy в конфиг не попадают и в подписках их нет.
  - `Sync` пишет копию сертификата и конфиг и, только если что-то поменялось, делает `systemctl try-reload-or-restart` (ExecReload службы шлёт контейнеру SIGHUP). Его вызывают панель при изменении пользователей и домена, `tigersb monitor` раз в 5 минут (так доходит продлённый сертификат) и `tigersb singbox run` перед стартом.
  - Сохранение протоколов: `sing-box check` в одноразовом контейнере без сети; перезапускается или перечитывает настройки только ядро, чьи настройки поменялись.
  - Перечитанный конфиг — это новый QUIC-слушатель: он не знает старых подключений и не шлёт им сброс, поэтому клиенты замечают обрыв только по таймауту простоя. В обоих inbound стоит `idle_timeout` 12 с вместо 30 по умолчанию; тихое подключение держат heartbeat TUIC и keep-alive Hysteria обеих сторон (10 с).
  - Hysteria 2: `obfs` Salamander с паролем из настроек (по умолчанию включён), `bbr_profile`, при заданных скоростях сервера `up_mbps`/`down_mbps` (тогда клиенты, сообщающие свою скорость, получают Brutal), `ignore_client_bandwidth`. Без Salamander в inbound стоит `masquerade: https://<домен>`: посторонний, пришедший по HTTP/3, видит заглушку сайта. Ссылка `hysteria2://пароль@адрес:порт/?sni=&obfs=salamander&obfs-password=`.
  - NaïveProxy: режим `network` (`tcp`, `quic`, `both`) и `bbr`. TCP — inbound `naive` на `127.0.0.1:10443` (`network: tcp`, TLS с ALPN `h2`, `http/1.1`) за edge, который держит публичный порт и ставит BBR: в sing-box нет настройки TCP-алгоритма. QUIC — inbound `naive-quic` на публичном UDP-порту (`network: udp`, ALPN `h3`, `quic_congestion_control` `bbr` или `cubic`). Пользователи `username`/`password` общие. Без CONNECT с дополнением и верного пароля sing-box закрывает подключение. Ссылки `naive+https://u<id>:пароль@адрес:порт?sni=<домен>&padding=true` и `naive+quic://…` с теми же параметрами; в профиле TigerSB это два транспорта, `naive` и `naive-quic` (приоритет 55), в обычной подписке — две ссылки.
  - Маршрут: `resolve`, затем отказ для частных адресов (`ip_is_private`), чтобы через VPN нельзя было достучаться до панели и соседей сервера. Статистики по пользователям нет: в официальной сборке нет `v2ray_api`.

- Mieru (`internal/singbox`, `MieruRuntime`, служба `tigersb-mieru`, `tigersb mieru`): официальный sing-box Mieru не умеет, поэтому он работает на [mbox](https://github.com/enfein/mbox) 1.14.3 (сборка sing-box от автора Mieru, GPL-3.0). Образа у mbox нет: установщик скачивает статический musl-бинарник из релиза, проверяет sha256 и кладёт в `/usr/local/lib/tigersb/mbox` (путь меняет `TIGERSB_MBOX`). Контейнер запускается из закреплённого образа sing-box с этим бинарником (`-v …/mbox:/usr/local/bin/mbox:ro --entrypoint /usr/local/bin/mbox`) и теми же ограничениями; конфиг в `/var/lib/tigersb/mieru`, сертификат не нужен.
  - Тот же `Runtime`, что у sing-box, с другими именем, контейнером, каталогом и `render` (`RenderMieru`); настройки Mieru лежат в `singbox.protocols` рядом с остальными.
  - Inbound `mieru` слушает один порт, поэтому диапазон (по умолчанию 2012–2022, не больше 100 портов) — это inbound на каждый порт и транспорт, тег `mieru-<tcp|udp>-<порт>`, с общим списком пользователей. Транспорт TCP, UDP или `BOTH` (оба: inbound на каждый порт по TCP и по UDP).
  - mbox по SIGHUP перечитывает конфиг, но новых пользователей Mieru не подхватывает (старые работают, новые нет). Поэтому у службы нет `ExecReload`, а `Sync` делает `systemctl try-restart`: подключения Mieru прерываются примерно на секунду.
  - Ссылка `mierus://u<id>:пароль@адрес?profile=TigerSB&port=2012-2022&protocol=TCP`. Домен не нужен, ссылка работает по IP. При `BOTH` две ссылки, с `protocol=TCP` и `protocol=UDP`; в профиле TigerSB это транспорты `mieru` (приоритет 60) и `mieru-udp` (65), как `naive` и `naive-quic`.

- Состояние протоколов (`health.Protocols`): для каждого из шести — включён ли, работает ли его контейнер, есть ли домен и сертификат, слушаются ли порты (для протокола за edge — и внутренний). Ничего не сохраняет; его показывают вкладка «Пользователи» и `/api/overview`.
- «Обзор» (`/api/overview`): состояние протоколов, сводка пользователей (из того же `usersState`, что и вкладка «Пользователи»), состояние ядер, edge и подписок, последний отчёт проверки, последний замер ресурсов и проверка обновлений.

- Подписки (`internal/sub`, служба `tigersb-sub`, `tigersb sub`) на `127.0.0.1:10086`. Caddy отправляет туда `/sub/*`; ответ 404 Caddy заменяет заглушкой (`handle_response`), недоступная служба тоже даёт заглушку (`handle_errors`, `file_server` со статусом 200).
  - Токен подписки — колонка `users.sub_token` (уникальный индекс), устройства — таблица `devices` (`UNIQUE(user_id, hwid)`). Новое устройство добавляется в транзакции, только пока их меньше лимита.
  - Ключ подписи Ed25519 — настройка `sub.key`, создаётся один раз (`INSERT … ON CONFLICT DO NOTHING`, поэтому панель и служба не создадут два разных).
  - User-Agent `TigerSB-…` получает конверт `{v, pk, payload, sig}` из `pkg/profile` клиента, остальные — base64 со ссылками `vless://` (те же ссылки разбирает `profile.ParseLink`, поэтому профиль и ссылки не расходятся).
  - Адрес устройства — последний `X-Forwarded-For` от Caddy; от других источников заголовок не принимается.

Занятые порты: 80 (Caddy без домена), 443 (edge), 8444 (Caddy), 10085 (API Xray), 10086 (подписки), 10441 и 10442 (Xray за edge), порт панели, 8443/UDP (TUIC), 443/UDP (Hysteria 2), 2443/TCP (NaïveProxy, держит edge) и 10443 (NaïveProxy за edge), 2012–2022/TCP (Mieru). Протоколам Xray доступны 443 и 1024–65535, кроме занятых; общим у двух протоколов может быть только 443, и тогда SNI должны различаться. TUIC и Hysteria 2 слушают UDP, поэтому могут стоять на том же номере порта, что и протокол Xray (Caddy HTTP/3 не включает, UDP 443 свободен), но не на одном порту друг с другом. NaïveProxy и Mieru по TCP не пересекаются с портами Xray, служебными портами и друг с другом, Mieru по UDP — с TUIC и Hysteria 2.

## План

- Маршруты: gRPC напрямую, XHTTP напрямую, каскад РФ → за границу по gRPC, XHTTP через Yandex CDN, TUIC через каскад (TUIC напрямую уже работает).
- Автовыбор: самый быстрый из gRPC, XHTTP и каскада. CDN включается, только если остальные недоступны (Xray balancer, `fallbackTag`).
- У каждого XHTTP-подключения через CDN свой домен; пользователей можно массово переносить на другой домен.
- Контроль устройств: лимит одновременных IP по всем узлам (HWID при выдаче подписки уже работает).
